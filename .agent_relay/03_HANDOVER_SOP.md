# 03 · 接力标准作业程序（HANDOVER SOP · 公开源码快照版）

> 读者：任何零对话历史、准备接手 Moyu 公开源码快照的 Agent。
> 目标：5 分钟内定位断点，30 分钟内可安全开始修改，不重复踩坑，不制造第二份事实源。
> 本文件是操作手册；宪章在 `00`，热状态在 `01`，历史决策在 `02`，冷启动指令在 `04`。
> 公开仓不包含 `AGENTS.md`、内部 QA 套件、发布工作流与内部工程脚本；本手册不得依赖这些缺失文件。

---

## 1. 接手读取顺序（强制）

1. `00_CHARTER.md`：不可变红线、技术栈与依赖审批规则。
2. `01_STATE.md`：当前状态、里程碑、精确断点、Next Immediate Action。
3. 本文件：环境自检、更新规范、提交协议。
4. `02_DECISIONS_AND_PITFALLS.md`：只读与当前任务相关的 ADR / Pitfall / 契约；不要通读全部历史。
5. `README.md` / `README.en.md`：产品说明与构建入口。
6. `docs/ARCHITECTURE.md`：公开架构概览。
7. 按需：相关源码、`.github/PULL_REQUEST_TEMPLATE.md`、`.github/RELEASE_NOTES_TEMPLATE.md`、`THIRD_PARTY_NOTICES.md`。

> 若 `01_STATE.md` 与本文件、`00_CHARTER.md` 冲突：以 `00` 与所有者当前指令为准；立即在 `01` 标注冲突并在 `02` 记录，不得自行扩大解释。

---

## 2. 五分钟定位与环境自检

> 首次接手至少完成 0)–3)；构建与格式检查按改动范围裁剪。公开仓没有内部 QA 套件；完整 QA 在维护者的完整工程环境执行。

```bash
# 0) 位置与身份
pwd
git remote -v
git status --short
git worktree list
git log -5 --format='%h %s'

# 1) 依赖（首次或 lockfile 变化时）
npm ci

# 2) 类型与 Rust 检查
npm run check

# 3) Rust 单测
npm run test:rust

# 4) 构建与格式（按改动选择）
npm run build
npm run format:check
```

**验证口径**

- 涉及 UI：同步六语字典、双主题与本地验证。
- 涉及后端命令/数据结构：同步 `docs/ARCHITECTURE.md` 与前端类型。
- 提交/PR 前：确认 `npm run check`、`npm run test:rust`、`npm run build` 与改动相关；Rust 改动另跑 `npm run format:check`。
- **禁止**把未运行的检查写成 PASS。报告使用 `VERIFIED / SIMULATED / INFERRED / UNKNOWN / BLOCKED`。
- L3（可见 GUI/桌面/系统级）必须获得所有者单独授权；无头结果不得冒充真实 GUI 覆盖。

**工作区保护**

- 现有未提交改动可能属于所有者或其它 Agent；不得用 `git stash`、`git checkout --`、强制推送、删分支清场。
- 开始前记录 `git status --short`；只 stage 自己拥有的文件；冲突显式写入 `01` 并通知所有者。

## 3. 状态判定（`01_STATE.md` 的状态机）

| 状态 | 判定标准 | 允许的下一步 |
|---|---|---|
| `GREEN` | 当前分支可编译、相关测试通过、断点清晰 | 继续实现或提交 |
| `RED` | 正在重构且暂时不可编译/测试失败 | 只允许收敛到 GREEN，不得开新功能 |
| `BLOCKED` | 外部条件阻塞（授权、Issue、依赖、环境） | 记录阻塞项与解除条件，等待所有者 |

- 状态必须附证据：命令、结果、执行级别（L0–L3）、时间。
- 本地未复验但 CI 通过时，写 `GREEN (CI 证据；本地复验 UNKNOWN)`，不得只写 GREEN。
- 发布阻塞项、L3 授权、未关闭的安全告警必须进入 `01` 的阻塞区。

---

## 4. 标准工作循环

1. **认领**：在 GitHub Issue 中 Assignee + `status:in-progress`；确认无其它写者。
2. **隔离**：按 `fix|feat|hotfix|chore/<issue>-<slug>` 建分支/Worktree；一个 Issue 一个分支。
3. **读契约**：查 `02` 中相关 ADR/Pitfall/Contract；查 `docs/ARCHITECTURE.md` 与相关源码。
4. **实现**：最小改动；不做范围外重构；不引入未批准依赖。
5. **验证**：按 §2 选择命令；UI 改动补六语；后端改动补架构说明与类型。
6. **更新 `01`**：覆盖为最新断点（见 §5）。
7. **提交**：按 §6 格式，只提交自己拥有的文件。
8. **交接**：按 §8 输出接力摘要。

---

## 5. `01_STATE.md` 更新规范

**何时更新**

- 每个原子任务完成、准备提交前。
- 开始新任务、切换文件焦点、遇到阻塞时。
- 设计变更写入 `02` 后。
- 收到“准备交接/保存状态”指令时。
- 交接前最后一步。

**怎么写**

- 覆盖写，不追加历史；控制在 100 行以内。
- 必填：状态、最后更新（ISO 时间）、分支/HEAD、当前文件与函数/组件、最后完成动作、Next Immediate Action、FIXME/TODO 的 `文件:行`。
- 只保留“接手者现在需要知道的”；历史原因、失败尝试、长篇分析放 `02`。
- 删除过期噪音；过期内容不是“保险”，而是误导。
- 不写“应该没问题”“大概通过”等未验证结论。

**推荐骨架**

```markdown
# 01 · 实时热状态

> 最后更新：YYYY-MM-DDTHH:mm:ss+08:00
> 分支 / HEAD：
> 状态：GREEN | RED | BLOCKED

## 里程碑
- [x] ...
- [/] ...
- [ ] ...

## 当前断点
- 文件 / 函数：
- 最后完成：
- Next Immediate Action：
- 阻塞项：

## FIXME / TODO
- `path:line` — ...

## 本轮验证
- ...
```

## 6. Git 微提交协议

**提交时机**

- 每完成一个原子步骤（编译通过/单测通过），先更新 `01`，立即提交。
- 禁止积攒多个功能一起提交。
- 只在对应 Issue 分支提交；`main` 不直接提交。

**公开仓边界**

- `origin/main` 是公开源码快照，只包含核心产品源码与构建配置。
- `.agent_relay/` 在公开仓必须自洽，不得引用 `AGENTS.md`、内部 QA 套件、发布工作流或生成状态文件。
- 不得把完整开发仓历史或内部工程文件推到公开仓。

**提交信息格式**

```text
feat(parser): 完成 AST 节点定义

- 新增节点类型与访问器
- 补充解析单测
- 更新 01 断点为 lexer 匹配

[RELAY] parser: 完成 AST 节点定义 | NEXT: 在 lexer.rs 中实现 token 匹配
```

- Subject 遵循 Conventional Commits 中文说明（`feat:` / `fix:` / `refactor!:` 等）。
- 正文 3–6 条中文要点；末尾保留 `[RELAY] <模块>: <动作> | NEXT: <下一步>`，供 `git log --grep='\[RELAY\]'` 检索。
- 提交前确认：不包含密钥、Cookie、请求头值、完整签名 URL、生成物、无关文件。

**半成品暂存（WIP Snapshot）**

- 跨文件重构且暂不可编译时：每改完一个文件，`git add <file>` 放入暂存区；正在写的焦点文件留在工作区（Unstaged）。
- 在 `01` 记录“已暂存文件 / 未暂存焦点文件 / 下一步”三栏，方便继任者区分“已改好待联调”与“正在写”。
- 不得为了“干净”而提交不可编译的半成品；紧急交接时提交 `wip:` 必须获得所有者同意，并在 `01` 标明。

**禁止**

- `git stash`、`git checkout --`、`git reset --hard`、强制推送、删除他人分支。
- `--no-verify`、跳过签名、跳过必需检查。
- 提交 `dist/`、`target/`、缓存或内部生成物。

## 7. `02_DECISIONS_AND_PITFALLS.md` 追加规范

- 只追加，不删除；被推翻的决策标记 `SUPERSEDED` 并指向新 ADR。
- 何时追加：架构/契约/依赖/发布流程变更；确认死胡同；跨模块字段/接口变更；所有者做出取舍。
- 每条必须有：日期、状态、背景、决策、放弃方案、后果/约束。
- 失败尝试写成“严禁再次尝试 X，因为会导致 Y”，不要只写“试过不行”。
- 不在 `02` 复制完整开发仓内部文档；只记录“为什么这样选”和“为什么不能那样做”。

## 8. 交接流程（准备换 Agent 时）

1. **停在安全点**：不要留下写到一半且无标记的文件；若必须中断，在 `01` 精确标注焦点文件与未完成逻辑。
2. **验证并记录**：跑当前任务相关的最低成本检查；记录命令、结果、执行级别；未跑的写 UNKNOWN。
3. **刷新 `01`**：状态、分支/HEAD、断点、Next Immediate Action、FIXME/TODO、阻塞项。
4. **追加 `02`**：本轮的设计变更、死胡同、新契约。
5. **整理 Git**：`git status --short`；按 §6 暂存/提交；记录未提交文件归属。
6. **输出接力摘要**（给下一位 Agent）：

```text
[RELAY HANDOVER]
分支 / HEAD：
状态：GREEN / RED / BLOCKED
最后完成：
当前断点（文件/函数）：
Next Immediate Action：
阻塞项：
本轮验证（VERIFIED/UNKNOWN/BLOCKED）：
未提交文件（staged / unstaged）：
相关 ADR / Pitfall：
```

7. **下一位 Agent**：按 §1 读取，运行 §2 自检，若与 `01` 不一致先修正 `01` 再动手。

---

## 9. 多 Agent 协作规则

- 按**文件所有权**切分；同一文件同一时间只有一个写者。
- 子代理只改授权文件；主代理负责集成、冲突处理与最终验收。
- 并行任务不得共享未提交的工作区；使用独立 Worktree/分支。
- 发现他人未提交改动时，不清理、不覆盖；在 `01` 记录并通知所有者。
- 冲突解决必须显式记录到 `02`，不得用清场式 Git 操作掩盖。

---

## 10. 交接前的快速自检（逐条确认）

- [ ] `00` 红线没有被我改写。
- [ ] `01` ≤100 行、状态真实、断点可执行。
- [ ] `02` 已追加本轮设计变更/死胡同（如有）。
- [ ] `git status` 中没有我造成的无关改动。
- [ ] 提交信息含 Conventional Subject 与 `[RELAY]` 正文。
- [ ] 未运行测试没有被写成 PASS。
- [ ] 没有推送 `v*` Tag，没有跳过门禁。
- [ ] 没有把路径/漫画名/Cookie/Token 写入日志或提交。
- [ ] 没有引入未批准依赖或第二套事实源。
- [ ] 没有引用公开仓不存在的内部文件。
- [ ] L3 操作有单独授权与清理记录（如有）。
